Integration Concepts

The foundation of everything in SAP CPI

What is Integration?

In the real world, companies use many different software systems from different vendors. These systems do not automatically communicate with each other. Integration is the process of making these systems exchange data automatically without human intervention.

Real World Example: A company uses Salesforce for sales, SAP S/4HANA for finance, and Workday for HR. When a new employee joins, their data needs to go into all three systems. Without integration, someone manually enters data three times — slow and error-prone. With integration, entering data once automatically updates all systems.

What is Middleware?

Middleware is a software system that sits between two or more systems and manages communication between them. SAP CPI is a middleware platform.

Without Middleware (Point-to-Point): Salesforce ←——→ SAP S/4HANA Salesforce ←——→ Workday SAP S/4HANA ←——→ Workday = Many direct connections, hard to manage With Middleware (Hub and Spoke): Salesforce ——→ [ SAP CPI ] ←—— SAP S/4HANA ↑ Workday = All systems connect to one central hub

What is a Message?

When systems communicate through CPI, they exchange messages. Every message has three parts:

PartDescriptionExample
HeaderMetadata about the messageContent-Type, sender info, timestamp
BodyThe actual data payloadOrder details, customer record
AttachmentOptional files attachedPDF invoice, image file

Synchronous vs Asynchronous

TypeBehaviorExample
SynchronousSender sends a message and waits for a response before continuingLike a phone call — you wait for the other person to respond
AsynchronousSender sends a message once and moves on without waitingLike sending an email — you send it and continue your work

What is an API?

An API (Application Programming Interface) is a defined way for one system to expose its data or functions so other systems can use them.

Analogy: A restaurant menu is an API. You (the client) look at the menu and order. The kitchen (the server) prepares your food and brings it out. You do not go into the kitchen directly — you use the defined interface (the menu).
Why This Matters in CPI: Every iFlow you build receives a message from a source system, processes it, and sends it to a target system. Understanding messages, middleware, and APIs is the foundation of every integration scenario.

Key Takeaways

  • Integration = making systems talk automatically
  • Middleware = central hub managing all system communication
  • Message = Header + Body + Attachment
  • Synchronous = sender waits for response
  • Asynchronous = sender does not wait
  • API = a defined interface to access system data or functions

XML

eXtensible Markup Language — the primary data format in SAP systems

What is XML?

XML (eXtensible Markup Language) is a text-based format for storing and transporting structured data. It uses tags to describe and organize data — similar to HTML but designed for data, not display.

Basic Structure

<!-- XML Declaration (optional but recommended) -->
<?xml version="1.0" encoding="UTF-8"?>

<order>                          <!-- Root Element -->
    <orderId>1001</orderId>
    <customer>                    <!-- Parent Element -->
        <name>Ahmed</name>          <!-- Child Element -->
        <city>Riyadh</city>
    </customer>
    <amount>5000</amount>
</order>

XML Rules

  • Every opening tag must have a closing tag: <name>Ahmed</name>
  • Tags are case sensitive: <Name> and <name> are different
  • There must be exactly one root element wrapping everything
  • Elements can be nested inside each other
  • Attribute values must be in quotes

Attributes

Attributes provide extra information about an element and are written inside the opening tag.

<order type="sales" status="pending">
    <amount currency="SAR">5000</amount>
</order>

Real World Example — Invoice XML

<invoice>
    <invoiceId>INV-2001</invoiceId>
    <vendor>
        <vendorName>Al Rajhi Trading</vendorName>
        <country>Saudi Arabia</country>
    </vendor>
    <items>
        <item type="product">
            <itemName>Laptop</itemName>
            <quantity>3</quantity>
            <price currency="SAR">4500</price>
        </item>
    </items>
    <totalAmount>13500</totalAmount>
</invoice>

Namespaces

Namespaces prevent naming conflicts when two XML documents are merged. You will see them frequently in CPI message mapping.

<ns0:order xmlns:ns0="http://company.com/sales">
    <ns0:orderId>1001</ns0:orderId>
</ns0:order>
Why XML Matters in CPI: SAP S/4HANA, IDocs, and SOAP messages all use XML. Message mapping in CPI works with XML structure. XPath and XSLT (covered later) both operate on XML.

Key Takeaways

  • XML stores structured data using opening and closing tags
  • Root element is the single outermost tag
  • Elements can contain child elements (nesting)
  • Attributes add extra info inside the opening tag
  • Namespaces use prefixes like ns0: to avoid naming conflicts

JSON

JavaScript Object Notation — the data format of modern REST APIs

What is JSON?

JSON (JavaScript Object Notation) is a lightweight text format for storing and transporting data. It uses key-value pairs and is simpler and lighter than XML. It is the standard format for modern REST APIs.

Basic Structure

{
    "orderId": "1001",
    "customer": {
        "name": "Ahmed",
        "city": "Riyadh"
    },
    "amount": 5000
}

Data Types in JSON

{
    "name": "Ahmed",         // String — text in double quotes
    "age": 30,              // Number — no quotes
    "isActive": true,       // Boolean — true or false
    "salary": 9500.50,      // Decimal number
    "middleName": null       // Null — no value
}

Arrays — Lists of Items

Square brackets [ ] represent a list (array) of items.

{
    "invoice": {
        "invoiceId": "INV-2001",
        "items": [
            {
                "itemName": "Laptop",
                "quantity": 3,
                "price": 4500
            },
            {
                "itemName": "Mouse",
                "quantity": 5,
                "price": 150
            }
        ],
        "totalAmount": 14250
    }
}

JSON vs XML Comparison

FeatureXMLJSON
FormatTags with opening/closingKey-value pairs
SizeHeavierLighter
ReadabilityMore verboseCleaner and simpler
AttributesYesNo
NamespacesYesNo
Used inSOAP, SAP IDocs, legacy systemsREST APIs, modern systems
Why JSON Matters in CPI: Modern third-party systems like Salesforce and ServiceNow send JSON. CPI can receive JSON, convert it to XML internally for processing, then send JSON back out. Groovy scripts inside CPI also read and manipulate JSON payloads.

Key Takeaways

  • JSON stores data as key-value pairs
  • Objects are wrapped in curly braces { }
  • Arrays (lists) are wrapped in square brackets [ ]
  • Keys are always in double quotes
  • Value types: String, Number, Boolean, Null, Object, Array
  • JSON is lighter and simpler than XML

REST and HTTP

The communication protocol powering modern API integrations

What is HTTP?

HTTP (HyperText Transfer Protocol) is the set of rules used to send and receive data over the internet. Every time you open a website, your browser uses HTTP to communicate with the server. In CPI, HTTP is the foundation of all REST API calls between systems.

HTTP Request Structure

// Every HTTP request has these parts:

METHOD   /resource/path   HTTP/1.1
Host: api.company.com
Content-Type: application/json
Authorization: Bearer abc123token

{
    "body": "data goes here"
}

HTTP Methods

MethodPurposeHas Body?Example
GETRead / fetch dataNoGet a customer record
POSTCreate new dataYesCreate a new order
PUTUpdate existing dataYesUpdate customer address
DELETEDelete dataNoDelete an invoice

HTTP Status Codes

After sending a request, the server returns a status code telling you what happened.

CodeMeaningCategory
200OK — request succeededSuccess
201Created — new record createdSuccess
400Bad Request — your request has an errorClient Error
401Unauthorized — authentication failedClient Error
403Forbidden — no permissionClient Error
404Not Found — resource does not existClient Error
500Internal Server Error — server problemServer Error
Simple Rule: 2xx = Success  |  4xx = Your mistake (client side)  |  5xx = Their mistake (server side)

What is REST?

REST (Representational State Transfer) is a set of rules for building APIs using HTTP. A REST API exposes resources (data) through URLs and uses HTTP methods to interact with them.

REST URL Structure

https://api.company.com/customers/1001
│         │               │         │
│         │               │         └── Record ID
│         │               └── Resource (collection name)
│         └── Server address
└── Protocol

REST API Example — Orders

ActionMethodURLBody
Get all ordersGET/ordersNone
Get one orderGET/orders/1001None
Create orderPOST/ordersOrder data in JSON
Update orderPUT/orders/1001Updated data in JSON
Delete orderDELETE/orders/1001None
Why REST and HTTP Matter in CPI: CPI has an HTTP Receiver adapter to call REST APIs. You configure the method (GET/POST/PUT/DELETE) inside the adapter. Status codes appear in CPI monitoring when integrations fail. HTTP headers like Content-Type and Authorization are set inside iFlows.

Key Takeaways

  • HTTP is the protocol for sending requests and receiving responses
  • Four main methods: GET, POST, PUT, DELETE
  • Status codes: 2xx success, 4xx client error, 5xx server error
  • REST is a set of rules for building APIs using HTTP and URLs
  • REST URLs follow the pattern: host / resource / id

SOAP and WSDL

The enterprise messaging protocol used heavily in SAP systems

What is SOAP?

SOAP (Simple Object Access Protocol) is a messaging protocol for exchanging structured data between systems using XML. It is older than REST but still heavily used in SAP and enterprise banking systems.

SOAP vs REST

FeatureSOAPREST
Data FormatXML onlyJSON or XML
StructureStrict and definedFlexible
Contract FileRequires WSDLOptional
SpeedHeavierLighter
Used inSAP, banks, legacy enterpriseModern APIs, mobile, web

SOAP Message Structure

<soap:Envelope xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/">

    <soap:Header>
        <!-- Optional: Authentication, session tokens, routing info -->
        <auth:token>abc123</auth:token>
    </soap:Header>

    <soap:Body>
        <!-- Mandatory: The actual request data -->
        <ord:CreateOrder>
            <ord:customerId>C001</ord:customerId>
            <ord:product>Laptop</ord:product>
            <ord:quantity>2</ord:quantity>
        </ord:CreateOrder>
    </soap:Body>

</soap:Envelope>

SOAP Envelope Parts

PartMandatoryPurpose
EnvelopeYesOuter wrapper for the entire SOAP message
HeaderNoAuthentication, session info, metadata
BodyYesThe actual request or response data
FaultNoError details — appears in Body when an error occurs

SOAP Fault — Error Response

<soap:Envelope>
    <soap:Body>
        <soap:Fault>
            <faultcode>soap:Client</faultcode>
            <faultstring>Invalid customer ID provided</faultstring>
        </soap:Fault>
    </soap:Body>
</soap:Envelope>

What is WSDL?

WSDL (Web Services Description Language) is an XML file that describes what a SOAP web service offers. It is the instruction manual for the service — telling you what operations exist, what input they need, what output they return, and where the service lives.

WSDL Key Sections

SectionPurpose
typesDefines the data structures used
messageDefines input and output for each operation
portTypeLists all available operations (functions)
bindingSpecifies SOAP version and encoding rules
serviceThe actual URL where the service is hosted
Why SOAP Matters in CPI: CPI has a dedicated SOAP adapter. You provide the WSDL URL and CPI automatically reads all available operations. SAP S/4HANA and SAP ECC expose many SOAP web services natively. SOAP messages appear as XML in CPI message monitoring.

Key Takeaways

  • SOAP is an XML-based enterprise messaging protocol
  • Every SOAP message has an Envelope containing Header and Body
  • Header is optional — Body is mandatory
  • Fault element appears in Body when an error occurs
  • WSDL is the instruction manual describing the SOAP service
  • portType section in WSDL lists all available operations

XPath

The language for navigating and extracting data from XML documents

What is XPath?

XPath (XML Path Language) is a syntax for navigating through an XML document and extracting specific values. Think of XML as a tree of data and XPath as the address or path to reach any specific branch or leaf in that tree.

Analogy: If XML is a building, XPath is the address. Instead of "123 Main Street, Floor 3, Room 7", you write "/building/floor[3]/room[7]" to find exactly what you need.

The XML Tree

<company>                         <!-- Level 1: Root -->
    <employee id="E01">           <!-- Level 2 -->
        <name>Ahmed</name>         <!-- Level 3 -->
        <department>IT</department>
        <salary>8000</salary>
    </employee>
    <employee id="E02">
        <name>Sara</name>
        <department>HR</department>
        <salary>9500</salary>
    </employee>
</company>

Basic XPath Syntax

XPath ExpressionWhat It Selects
/companyThe root element
/company/employeeAll employee elements
/company/employee[1]First employee only (Ahmed)
/company/employee[2]Second employee only (Sara)
/company/employee[1]/nameAhmed's name element
/company/employee[2]/salarySara's salary = 9500
Important: XPath index starts at 1, not 0. The first item is [1], not [0].

Selecting Attributes with @

XPath ExpressionWhat It Selects
/company/employee/@idThe id attribute of all employees
/company/employee[1]/@idValue = E01
/item/price/@currencyThe currency attribute value = SAR

Filtering with Conditions

XPath ExpressionWhat It Selects
/company/employee[department='IT']Employee in IT department
/company/employee[salary>8000]Employees with salary above 8000
/company/employee[name='Sara']/salarySara's salary = 9500

Double Slash — Search Anywhere

XPath ExpressionWhat It Selects
//nameAll name elements anywhere in the document
//employeeAll employee elements regardless of depth
//price[@currency='SAR']Price elements with currency SAR anywhere

Useful XPath Functions

FunctionPurposeExample
text()Get the text value/company/employee[1]/name/text() = Ahmed
count()Count elementscount(/company/employee) = 2
contains()Check if string contains valuecontains(/name, 'Ah') = true for Ahmed
Why XPath Matters in CPI: The Content Based Router in CPI uses XPath to decide which path a message takes. Message mapping uses XPath to extract source values. Groovy scripts use XPath to read XML data. The Filter step uses XPath conditions to allow or block messages.

Key Takeaways

  • XPath navigates XML using path expressions like addresses
  • / means navigate to a direct child
  • // means search anywhere in the document
  • @ selects an attribute value
  • [n] selects by position — index starts at 1
  • [condition] filters elements by a condition
  • text() extracts the text value of an element

XSLT

eXtensible Stylesheet Language Transformations — transform XML to XML

What is XSLT?

XSLT (eXtensible Stylesheet Language Transformations) is a language used to transform one XML document into a different XML structure. It takes a source XML, applies transformation rules, and produces an output XML with a different structure.

Analogy: Imagine you receive a letter in German but need to send it in English with a different layout. XSLT is the translator and formatter — it reads the original, converts the content, and produces the new version automatically.

Why XSLT is Needed

System A and System B both use XML, but their structures are completely different. XSLT transforms System A's XML format into System B's XML format.

Source XML (System A format) ↓ [ XSLT Transformation ] ↓ Target XML (System B format)

Simple Example — Renaming Elements

Source XML (from System A):

<order>
    <orderNumber>1001</orderNumber>
    <customerName>Ahmed</customerName>
    <totalValue>5000</totalValue>
</order>

Target XML needed (by System B):

<purchaseOrder>
    <poId>1001</poId>
    <buyer>Ahmed</buyer>
    <amount>5000</amount>
</purchaseOrder>

XSLT to transform it:

<xsl:stylesheet version="1.0"
    xmlns:xsl="http://www.w3.org/1999/XSL/Transform">

    <xsl:template match="/">
        <purchaseOrder>
            <poId>
                <xsl:value-of select="/order/orderNumber"/>
            </poId>
            <buyer>
                <xsl:value-of select="/order/customerName"/>
            </buyer>
            <amount>
                <xsl:value-of select="/order/totalValue"/>
            </amount>
        </purchaseOrder>
    </xsl:template>

</xsl:stylesheet>

Key XSLT Elements

ElementPurpose
<xsl:stylesheet>Root element — the container for the entire XSLT
<xsl:template match="/">Matches the root of the source XML and starts transformation
<xsl:value-of select="...">Reads a value from the source XML using XPath
<xsl:for-each select="...">Loops through multiple elements (like a list of items)
<xsl:if test="...">Conditional — only outputs if condition is true
<xsl:choose>Like if/else — multiple conditions

Looping Example — Multiple Items

<xsl:for-each select="/invoice/items/item">
    <lineItem>
        <product>
            <xsl:value-of select="itemName"/>
        </product>
        <qty>
            <xsl:value-of select="quantity"/>
        </qty>
    </lineItem>
</xsl:for-each>
Why XSLT Matters in CPI: CPI has a dedicated XSLT Mapping step inside iFlows. When source and target XML structures are very different, XSLT handles the transformation. It is more powerful than simple message mapping for complex XML restructuring scenarios.

Key Takeaways

  • XSLT transforms one XML structure into a different XML structure
  • It uses XPath expressions to read values from source XML
  • xsl:template defines the transformation rules
  • xsl:value-of extracts a value from the source
  • xsl:for-each loops through repeated elements
  • xsl:if adds conditional logic to the transformation

Groovy Scripting

Writing custom logic inside SAP CPI iFlows

What is Groovy?

Groovy is a scripting language that runs on the Java Virtual Machine (JVM). It is simpler than Java, supports dynamic typing, and can use any Java library. In SAP CPI, Groovy is used to write custom logic inside iFlows that cannot be done with standard mapping steps.

Groovy vs Java — Key Differences

FeatureJavaGroovy
Type declarationMandatory: int age = 30;Optional: def age = 30
SemicolonsRequiredOptional
String interpolationNot built-inBuilt-in: "Hello ${name}"
Runs onJVMJVM
Use in CPINot used directlyScript step in iFlows

Groovy Basics

// Variables — no type needed, use 'def'
def name = "Ahmed"
def age = 30
def isActive = true

// String interpolation — use ${} inside double quotes
println "Hello, ${name}! You are ${age} years old."

// Lists
def fruits = ["apple", "banana", "cherry"]
fruits.each { println it }

// Maps (like JSON objects)
def person = [name: "Sara", city: "Riyadh"]
println person.name

Groovy Script Structure in CPI

Every Groovy script in CPI follows this structure:

// Required import for CPI message handling
import com.sap.gateway.ip.core.customdev.util.Message

// The main function CPI calls — must always exist
def Message processData(Message message) {

    // Read the message body
    def body = message.getBody(String)

    // Read a message property
    def orderId = message.getProperty("orderId")

    // Read a message header
    def contentType = message.getHeader("Content-Type", String)

    // Modify the body
    def newBody = "Modified: ${body}"
    message.setBody(newBody)

    // Set a property
    message.setProperty("status", "processed")

    // Always return the message
    return message
}

Reading and Writing the Message Body

// Read body as String
def body = message.getBody(String)
println body

// Set a new body
message.setBody("<status>success</status>")

Working with Headers and Properties

OperationCode
Read a headermessage.getHeader("name", String)
Set a headermessage.setHeader("name", "value")
Read a propertymessage.getProperty("name")
Set a propertymessage.setProperty("name", "value")
Read bodymessage.getBody(String)
Set bodymessage.setBody("new content")

Conditional Logic

// if / else
def amount = 5000

if (amount > 3000) {
    message.setProperty("category", "high-value")
} else {
    message.setProperty("category", "standard")
}

Logging in Groovy — for Debugging

import groovy.util.logging.*

// Write to CPI message processing log
def messageLog = messageLogFactory.getMessageLog(message)
messageLog.addAttachmentAsString("Debug Info", "Order received: ${orderId}", "text/plain")
Why Groovy Matters in CPI: When standard CPI steps (Content Modifier, Message Mapping) are not enough, Groovy fills the gap. Common uses: dynamic value calculation, conditional logic, reading/writing headers and properties, custom error handling, parsing JSON payloads, and calling utility functions.

Key Takeaways

  • Groovy is a JVM scripting language — simpler than Java
  • Use def to declare variables — no type needed
  • Every CPI script must have a processData(Message message) function
  • Read the body with message.getBody(String)
  • Set the body with message.setBody("content")
  • Use getProperty/setProperty for message properties
  • Always return the message at the end of the function

Analogy: Think of SAP BTP as a shopping mall. SAP Integration Suite (CPI) is one shop inside that mall. The mall provides the building, electricity, security, and infrastructure — the shops provide specific services.

OData Basics

SAP's REST standard for accessing S/4HANA and Business Suite data

What is OData?

OData (Open Data Protocol) is a REST-based protocol created by Microsoft and heavily adopted by SAP. It is a standardized way to expose and consume data from SAP systems like S/4HANA, SuccessFactors, and Ariba through REST-style APIs.

Analogy: Think of OData as a very smart REST API that comes with built-in features — filtering, sorting, paging, and relationship navigation — all through the URL itself, without needing custom code on the server.

OData vs Regular REST

FeatureRegular RESTOData
ProtocolCustom per APIStandardized
FilteringCustom implementationBuilt-in via URL: $filter
SortingCustom implementationBuilt-in via URL: $orderby
PagingCustom implementationBuilt-in via URL: $top, $skip
MetadataNo standardBuilt-in: $metadata endpoint
Used inGeneral APIsSAP S/4HANA, SuccessFactors, Ariba

OData URL Structure

https://host/sap/opu/odata/sap/API_BUSINESS_PARTNER/A_BusinessPartner
│                           │                      │
│                           │                      └── Entity Set (the data collection)
│                           └── Service Name
└── SAP OData base path

OData Query Options — Filtering with URL

OData lets you filter, sort, and page data directly in the URL:

Query OptionPurposeExample
$filterFilter records?$filter=Country eq 'SA'
$selectChoose specific fields?$select=BusinessPartner,Name
$topLimit number of records?$top=10
$skipSkip records (for paging)?$skip=20
$orderbySort results?$orderby=Name asc
$expandInclude related data?$expand=to_Address
$formatResponse format?$format=json

OData Request Examples

// Get all Business Partners
GET /A_BusinessPartner

// Get one specific Business Partner
GET /A_BusinessPartner('BP001')

// Get Business Partners from Saudi Arabia only
GET /A_BusinessPartner?$filter=Country eq 'SA'

// Get top 5 Business Partners, only name and ID fields
GET /A_BusinessPartner?$top=5&$select=BusinessPartner,BusinessPartnerFullName

// Get Business Partners sorted by name, response in JSON
GET /A_BusinessPartner?$orderby=BusinessPartnerFullName asc&$format=json

OData Metadata

Every OData service has a $metadata endpoint that describes all available entity sets, fields, and relationships. It is the WSDL equivalent for OData.

// Access metadata to see all available entities and fields
GET /API_BUSINESS_PARTNER/$metadata

OData HTTP Methods

MethodOData ActionExample
GETRead dataRead a sales order
POSTCreate new recordCreate a business partner
PUTFull updateReplace entire record
PATCHPartial updateUpdate only specific fields
DELETEDelete recordDelete a sales order item
CSRF Token: SAP OData services require a CSRF (Cross-Site Request Forgery) token for write operations (POST, PUT, PATCH, DELETE). You first call GET with header x-csrf-token: fetch to get the token, then include it in your write request header.

Common SAP OData APIs

API NamePurpose
API_BUSINESS_PARTNERManage business partners / customers / vendors
API_SALES_ORDER_SRVCreate and manage sales orders
API_PURCHASEORDER_PROCESS_SRVManage purchase orders
API_MATERIAL_DOCUMENT_SRVGoods movements and material documents
Why OData Matters in CPI: CPI has a dedicated OData adapter for connecting to SAP S/4HANA. You can read master data (customers, materials) and transactional data (orders, invoices) from S/4HANA using OData. The OData adapter handles CSRF token fetching automatically. Most real-world CPI scenarios involve reading from or writing to S/4HANA via OData.

Key Takeaways

  • OData is a standardized REST protocol adopted heavily by SAP
  • It adds built-in filtering, sorting, and paging via URL query options
  • $filter, $select, $top, $skip, $orderby, $expand are key query options
  • $metadata endpoint describes all available data in the service
  • Write operations (POST/PUT/PATCH/DELETE) require a CSRF token
  • CPI has a dedicated OData adapter for connecting to S/4HANA
